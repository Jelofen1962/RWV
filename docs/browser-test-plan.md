# Browser capability smoke test (native device)

Run each generated app on its target OS with the actual WebView runtime. The CI compilation/tests do not exercise native GUI or credential dialogs.

1. Open an HTTPS test site with a disposable account. Sign in and save the login: accept WebView2's native prompt on Windows; on Linux use Passwords, Save, close/reopen, then copy each field; on Android enable a compatible system Autofill provider and use its save/fill prompt. Verify separate HTTPS origins cannot retrieve one another's saved login. Never test with real credentials on a public demo site.
2. Use a test site that sets a persistent first-party cookie, localStorage, IndexedDB and (on secure contexts) service-worker Cache Storage. Close and restart the app with the same name/origin and profile. Confirm persistent storage survives, subject to engine policies. A session cookie or sessionStorage may expire on close; website sign-in also depends on server expiration.
3. Rebuild with the same name/origin. On Android, use the same application ID and signing key and increment the version code; install as an update, not a fresh install. Confirm profile data survives.
4. On Android, test a user-initiated popup, file upload, ordinary HTTPS download, zoom, Back/Forward and Reload. A non-user-initiated popup should be blocked. Try a cross-origin iframe's permission request, which should be denied. For a top-level HTTPS page, deny and then allow camera/mic/location and confirm each follows the Android runtime permission result. Check that an HTTP page cannot obtain those permissions through RWV.
5. On Android, third-party cookies are off by default. Only enable them when needed for a trusted site, and check that the option persists on restart. Test website-data reset and use Android App info > Storage > Clear storage for a complete reset. System password-manager records are separate.
6. Test sites requiring external-browser-only features in the system browser. Do not assume embedded WebViews have parity with a full browser: browser extensions, DRM, some OAuth providers, browser sync, push, WebAuthn, downloads, device APIs and screen sharing depend on engine/OS/site policy.

7. Cold-launch on Android 6–11 and Android 12+ (light and dark device themes). Confirm the Android 12+ system starting window is white and icon-free, the shared splash displays the correct logo and name with the bottom credit and animated bar, and the site opens without a splash entry in its Back history. Test offline with embedded Poppins, simulate a failed build-time font download, test slow and unavailable websites, rotate the device, and verify that the splash clears within the five-second fallback. Verify HTTPS website font requests independently in a debug/test build.

8. Build each platform twice, with fullscreen off and on, using the same app identity. Confirm Android never reserves a toolbar margin, and normal mode retains OS bars. In fullscreen, verify OS bars can be revealed by swiping and the keyboard can open. Use Back to navigate history and Back at the start of history to open the options dialog; test fullscreen toggle and Exit app. Confirm Windows/Linux start in borderless fullscreen when selected and can be closed through OS shortcuts.
9. On Android API 26+, test with and without a configured Autofill provider. Without one, the setup prompt appears once; declining it does not prevent browsing. With one, no setup prompt appears. On a supported login form, verify the provider's native fill and save UI works, including after relaunch, in normal and fullscreen modes. Provider UI may be inline rather than a popup. On API 23–25 no system Autofill setup is offered.
